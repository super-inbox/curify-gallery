## S01

**标题：AI技术栈，一张图看懂九层分工**

一个 AI 应用背后，除了模型，还有哪些东西？这张偏生成式 AI 应用的 Stack 图，可以当作入门地图。我习惯按职责来读，而不是从上到下背工具名。

① 模型：理解输入、生成内容，例如 Claude、Qwen。
② 推理与访问：把模型变成可调用的服务，例如 Ollama、vLLM。
③ 编排：决定先检索、再调用工具、还是继续提问，例如 LangGraph、LlamaIndex。
④ 工具与协议：让模型接触外部系统，例如通过 HTTP API 或 MCP 访问业务工具。
⑤ 记忆：保存需要跨轮次或跨会话使用的信息，例如用数据库加明确规则管理用户偏好，或了解 Mem0。它与模型的 KV Cache 是两回事。
⑥ 检索存储：存放可查找的资料，例如 pgvector、Elasticsearch。
⑦ Embedding 与重排：前者把内容转成便于比较的向量，后者对候选资料再排一次序，例如 Sentence Transformers、跨编码器重排模型。
⑧ 数据提取：从 PDF、网页等内容中提取可用信息，例如 Docling。
⑨ 评估与观测：检查答案、追踪调用和耗时，例如测试脚本加 Langfuse。

对准备转入 AI 的人，我建议每一层至少亲手试过一两个代表工具，知道输入输出是什么、能解决什么问题。不用掌握图上全部工具，也不用每个应用都装齐九层。

再做一个端到端项目：企业制度助手。用 Docling 读文件，切成段落并生成向量，存入 pgvector；提问时取回相关段落，让模型附依据回答，再用固定问题集检查答案并记录耗时。先跑通这一条链。

有“查询剩余假期”的需求，再接业务工具；要长期记住表达偏好，再加记忆。复杂分支多了，再考虑编排框架。这样选型才有具体理由。

## S02

**标题：时间序列，也有自己的基础模型了**

销量、用电量、设备温度，这些按时间排列的数字，是统计学很熟悉的研究对象。如今，它们也成了 Foundation Model（基础模型）的应用方向。

传统方法里，指数平滑会利用历史水平、趋势和季节性；ARIMA 则刻画序列自身及误差的时间关系。我们往往围绕目标序列建模，再估计参数。

时间序列基础模型把一部分学习提前了：先在大量序列上预训练，再把已有能力迁移到新的序列。某些模型可以直接预测，也就是 zero-shot；有些任务还可以进一步微调。它们不一定是聊天模型，也不一定需要先把数字写成一段自然语言。

图里的 Timestral，可以分成上下两部分看：上面是预训练，学习不同序列的变化模式；下面是应用，把商店的数据交给训练好的模型。

销量是要预测的目标。客流量可以提供历史线索，已经排好的促销则是提前知道的未来信息。这些额外线索叫“协变量”。输出也可以是一组分位数，让你看到一个范围，而不只有一个确定数字。

这正是统计与 AI 相交的地方：模型能迁移经验，但趋势、季节性、时间顺序和不确定性仍然重要。促销计划可以提前知道，明天真实客流不能假装已经知道。

想动手，可以拿一份按天的销量数据，用早期数据预测后期，比较“和上周同一天一样”、一个传统统计模型和一个基础模型。观察误差，也观察预测区间是否合理。新模型带来的是新的候选方法，不是省掉统计判断。

## S03

**标题：混合检索，两个排名怎么合成一个**

知识库、文档助手、很多 Agent，都要先把资料找对，再继续回答或行动。Hybrid Retrieval（混合检索）是这个底座里很实用的一块。

图里是一个常见组合：BM25 按词项匹配及其统计特征评分，适合抓住专有名词、编号等线索；embedding-based 检索把问题和文档编码为向量，寻找语义相近的内容。两路可以互补。

接下来有一个具体问题：两路分数的尺度不同，不能随手直接相加。怎么合并？

RRF，全称 Reciprocal Rank Fusion（倒数排名融合），用排名代替原始分数。每一路给文档贡献 1 / (k + 排名)，再把贡献加起来。这里按图取 k=60，排名从 1 开始；某一路没检索到的文档，在那一路贡献为 0。

小例子：BM25 的前三名是 A、B、C；向量检索的前三名是 C、A、D。

A：1/61 + 1/62 ≈ 0.03252
C：1/63 + 1/61 ≈ 0.03227
B：1/62 ≈ 0.01613
D：1/63 ≈ 0.01587

合并后是 A、C、B、D。A 在两路都靠前，因此排到第一。这里不需要把 BM25 分数和向量相似度校准到同一尺度；k 也不是所有系统都必须取 60。

可以做个小练习：找 20 份短文档、写 10 个问题并标出正确资料。分别取两路 top-3，用上面的公式融合，再检查各方法的前三名是否包含正确资料。额外记录耗时，看看融合改善了什么、又漏掉了什么。

这套方法可以用于手册、报告、政策文件等检索；不同数据也可能需要不同组合。下一篇再看代码场景里 grep 的作用。

## S04

**标题：AI写代码，为何还在用grep？**

讲到 AI 检索，很多人想到的是：先把资料变成向量，再做语义搜索。可在 Coding Agent 里，我们又看到了一个很朴素的工具——grep，也就是按文字或模式找内容。

Anthropic 介绍 Claude Code 时，明确谈过用 grep、glob 这类工具按需寻找文件。glob 可以理解为“按文件名找文件”，grep 则是在文件内容里找线索。这里并不一定需要先给整个仓库建一套向量索引。

这件事有意思的地方，是代码自带很多可追踪的路标：函数名、路径、报错信息、调用位置。找“退款失败”的逻辑，可以先查 refund，看到相关函数后再查它在哪里被调用，读完上下文继续缩小范围。

如果团队叫它“退单”，代码却叫 refund，就补上别名和不同表达；常用目录过滤也可以封装成命令快捷方式。这是帮助搜索走对路，不是让 grep 自动理解语义。真正起作用的，是 Agent 根据每轮结果继续寻找。

所以，上一条的 BM25 加向量检索，是一种常见组合。更广义地设计检索系统，候选工具还可以有代码符号、目录、表格查询和图片搜索。先问数据长什么样、任务要找什么，再决定用什么组合。

代码里的精确名字适合文本查找；用户用日常语言描述功能时，语义检索可能提供另一条线索。仓库很大、命名不清或依赖复杂时，也不能假定 grep 总是更省。

## S05

**标题：长对话为什么需要KV Cache**

用 GPT 这类对话模型时，我们会贴一篇长文，再连续追问：“总结一下。”“展开第三点。”“换成表格。”模型为什么不用每生成一点内容，就把前面所有内容重新算一遍？

先看图里的两个阶段。

Prefill：处理这次输入，计算注意力需要的 Key、Value 等中间结果。
Decode：逐步生成新 token。token 可以是一个字、词的一部分或其他片段，并不总等于一个字。KV Cache 把历史 Key、Value 留下来，让后续生成复用它们，减少重复计算。

它缓存的是计算结果，不是把完整答案存起来；也不是聊天软件保存的“用户记忆”。

长输入还有另一层复用机会：下一次请求如果仍以同一份长资料开头，服务端在支持前缀缓存且命中的情况下，可以复用相同前缀的 KV，少做一段输入处理。不是所有产品、每次对话都会命中；这里讲的是通用机制，不推断某个聊天产品的内部实现。

那修改输入后呢？对于常见的自回归 Transformer，如果只在末尾补一个问题，前面没变的前缀可能继续复用；如果改了中间一句话，修改点之后的计算依赖已经变了，通常要从变化处重新处理。具体复用边界还取决于缓存分块等实现。

所以，长上下文不只是“模型能装下多少内容”，也涉及“哪些内容算过、还能不能复用”。缓存能节省计算，但要占内存或显存；前缀复用主要减少重复读输入的工作，并不让后面的每个新 token 都免于计算。

## S06

**标题：模型上线推理，背后的三种工具**

很多人知道模型训练好了，要放到线上做推理；但从“加载模型”到“稳定接住请求”，中间的 inference infrastructure（推理基础设施）往往不熟悉。

我会用三个工具讲这层系统。它们不是三种互斥的模型架构，而是侧重点不同的运行与服务方案。

**Ollama：先把运行和调用这件事变简单。**
它方便拉取模型、在本机运行并通过接口调用；量化模型还能降低内存需求，但质量和速度要实测。适合个人电脑上的文档问答、学习实验、内部原型。它也支持并发，并不等于“只能单用户”；主要看硬件、模型和配置是否撑得住。

**vLLM：把显存和批处理用得更有效。**
PagedAttention 把 KV Cache 分块管理，减少预留空间与碎片浪费。连续批处理允许完成的请求退出、新请求加入，让不同长度的任务更好地共享计算资源。它也支持前缀缓存。
适合多人同时使用的问答服务、批量生成等。加载支持的视觉语言模型后，也能做图片问答、文档图像理解；vLLM 是服务引擎，本身不赋予模型视觉能力。

**SGLang：关注重复上下文和复杂生成流程。**
其 RadixAttention 用树状结构管理可复用的前缀 KV。多个请求有相同开头时，能少做重复计算。例如客服共享一份长政策、Agent 的不同分支共享一段任务背景，值得测试这种复用带来的收益。
它同样是通用服务框架，不只适合 Agent；vLLM 也能复用前缀，不能把这项能力说成独占。

我的选型起点是负载：本地学习先把链路跑通；多人服务看并发与显存；重复长背景看缓存命中；多模态先核对模型和输入类型支持。然后固定模型、硬件与精度，比较首 token 等待、输出速度和高峰时的响应。

## S07

**标题：AI实验室排位，为什么总在变**

看 AI 实验室的 tier list，我第一反应不是记住名次，而是想看：这张图放到下个月，还有多少位置不变？

这个赛道很像一场持续的军备竞赛。训练、后训练、算力、人才和产品交付都在投入；但外界看到的进展不是一条平滑曲线，而是一次次集中发布。沉默一段时间，不一定代表停下来了。

以本轮能核实的进展为例：Meta 在推进 Muse 系列，10月27日还与 NVIDIA 公布了训练和推理方面的合作；Moonshot 的 Kimi K3 则把原生视觉、长上下文和代码任务作为重要方向。不同公司会从不同能力切入，重新争夺关注。

我的看法是，值得按周跟踪变化，但别把每周的热度当成永久的座次。这里的 top tier，到底是通用能力、代码能力、多模态，还是开放模型生态？选不同标准，就可能得到不同名单。

素材里的榜单把 Anthropic、OpenAI 放在 Frontier，把 Google DeepMind、Meta、Moonshot 放在 n-1，还把 Microsoft、Amazon 等放得更后。但它来自受访者的判断，不是一套所有实验室同条件参加的测验。它更适合引出争议，而不是终结争议。

说一家实验室“被落下”，我会看它是否连续多轮没能缩小能力差距、能否持续交付可用模型，以及有没有形成自己领先的方向。不能只凭一次没发布，或者一张总榜，就宣布出局。

如果现在让你重排：谁属于第一梯队？谁正在追上来，谁是真的逐渐掉队？也说说你看的维度——研究、代码、多模态还是生态。

## S08

**标题：模型越来越强，AI创业还能做什么**

看到“模型公司对比 SaaS”的图，最容易问：模型这么强了，应用还有价值吗？

我更想换个问法：客户买的到底是什么？

一个模型能起草邮件，不等于它已经接入客户的权限系统、理解业务流程、处理失败重试，并留下可以追查的记录。就像买了一台很好的发动机，还需要把它装成一辆适合用途的车。

我的判断是：如果产品主要靠“模型暂时做不到的某一步”，就要认真考虑能力升级带来的压力。如果它能持续把复杂流程变成可交付的结果，价值还要看接入成本、可靠性和客户愿不愿意继续付费。

这里不是在用估值证明谁会赢。估值反映预期，收入反映特定期间的经营结果，比较时还要统一时间和口径。

对 AI 创业者，一个值得写下来的问题是：假设底层模型下个月更强、更便宜，我们的客户为什么还需要我们？
