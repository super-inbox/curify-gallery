## 为什么原文件会被要求转曲

deck 是 headless Chromium 打印出来的（见 `../deck/build.py`）。Skia 把 PingFang SC
嵌成了 **Type 3** 字体——印刷厂在 Acrobat 文档属性 → 字体里看到的 `TJFont_10 / 类型: Type 3`
就是这个。Type 3 不是常规 CID 字体，很多 RIP 处理不了，所以要求转曲。

## 两个必须记住的参数

```
-dNoOutputFonts   把每个字形转成矢量路径 —— 转曲本身
-dNOCACHE         没有它，Ghostscript 的字形缓存会把少数几个汉字
                  悄悄栅格化成 720dpi 1-bit 位图而不是转成曲线，
                  而且每次跑栅格化的是不同的字。必须加。
```

图片走 `-dPassThroughJPEGImages` 且关掉所有降采样，所以转曲不损失图片质量。

出血版每页单独跑一遍 gs：gs 在这里不会可靠地递增 `/BeginPage` 的页计数，
所以底色只能按页写成常量，不能用页码索引数组（试过，九页全刷成了封面的深蓝）。
每页底色都是纯色（`--navy` / `--cream` / `--paper`），已跟渲染出来的页面四角逐页核对过。

## 已知问题：图片分辨率

5 张图低于 300ppi 印刷标准：

| 页 | 实际 ppi |
|---|---|
| P1 封面「影像」缩略图 | **173** |
| P4 | 218 |
| P7 | 255 |
| P5 / P7 | 283 |

**重新构建修不了这个** —— 上限在素材本身：`assets/vid_cult_a.jpg` 原图只有 1100×618，
`build.py` 的 `MAX_W = 1000` 只是又削了一点。44 个素材里只有 4 个宽度 ≥1600px。
真要修得重新生成这几张素材。数字印刷下 173ppi 会略微发虚，但通常还能接受；
如果是胶印且客户在意，先换素材再重跑。

## 还没确认的两件事

- **色彩模式**：目前是 RGB（带 ICC）。国内厂做胶印一般要 CMYK，
  但转 CMYK 必须知道他们的输出色彩配置文件，瞎转会让封面的深蓝 `#101F3C` 偏色。
  等印刷厂给了 profile 再转。
- **出血**：印刷厂没提，但 9 页里有 6 页是满版底色（封面/封底深蓝、4 页米色），
  不给出血的话裁切偏一点就会在边上露白边。所以备了出血版。
  ⚠️ 出血版**第一版有黑边**，见下节；现在的脚本已经修好，重跑即可。

**源文件留着别丢** —— 转曲后文字不能再编辑/搜索。要改内容改 `../deck/intro_src.html`
然后 `python3 build.py`，再跑一遍这个脚本。

## 已修：出血版的黑边（2026-09-01）

**症状**：出血版沿成品边缘一圈细黑线，A4 版没有。

**原因不在出血代码里，在源 PDF 的页边**。headless Chromium 打出来的页面边缘并不干净——
9 页**每一页**都有（300dpi 实测）：

| 边 | 实际内容 |
|---|---|
| 下 | 1px `#6B6B76` 实线（不透明，深蓝页和白底页量到同一个值） |
| 右 | 一条同类的线 + 约 2px 未上色的白 |
| 上 | 约 3px 未上色的白（有底色的页面上才看得出来） |
| 左 | 干净 |

A4 尺寸下这些东西正好压在裁切线上，裁刀直接切掉，谁也看不见。
**一旦把同一页居中放到 216×303 的大纸上，它们就整体往里挪了 3mm——落到新的裁切线上，
于是印出来就是绕成品一圈的细黑框。** 加底色垫背解决不了：垫的是页面**外面**，
黑线在页面**里面**。

**修法（脚本 step 3a）**：垫之前先把四边各切掉 1.5pt（0.53mm）。
`pdfwrite` 会把内容裁到固定 media，所以「更小的 media + 负的 `/PageOffset`」就是一次裁切。
再以 `10.00394 = 8.50394(3mm) + 1.5(裁掉的量)` 偏移放回大纸，**画面位置和裁切前完全一致**。
1.5pt 约为最宽伪影（3px@300dpi = 0.72pt）的两倍。之所以安全，是因为每页边缘都是纯底色，
垫的底色会把切掉的那圈原样补回来。

**试过但不行的两条路**（都实测过，别再走一遍）：

| 做法 | 结果 |
|---|---|
| 在 `/BeginPage` 里 `rectclip` 到内缩的矩形 | **无效**。pdfwrite 忽略 BeginPage 设的裁剪路径，黑线原封不动 |
| 在 `/EndPage` 里用 `eofill` 画一圈底色边框盖住 | **更糟**。pdfwrite 在 EndPage 阶段会丢掉页面内容，输出只剩一个空的深蓝边框 |

**验收**：9 页逐页 300dpi 渲染，四边各取 5 条扫描线，检查距纸边 1–45px 内是否有偏离底色
超过 12 的像素。修完只剩水印笔画（属于设计本身），伪影 0 条。

**一页的对照样张**在 `bleed-hairline-case/`：`p1-before-hairline.pdf` /
`p1-after-fixed.pdf` / `corner-before-after.png`（右下角 14.4mm 见方，4 倍放大，红线是裁切线）。

叙述版记录：`curify-frontend/docs/client-projects/print-prepress-bleed-hairline.md`。

## 仍未做：TrimBox

出血版的 `TrimBox` 现在等于 `MediaBox`（216×303），**没有标出 210×297 的成品框**。
规范的出血 PDF 应该带 TrimBox，印厂的 RIP 才知道往哪切。本机没有 `qpdf` 也没有 `pikepdf`，
gs 的 pdfwrite 也不直接写 TrimBox，所以暂时靠口头/邮件说明「成品 210×297，四边各 3mm 出血」。
装上 `pikepdf` 之后是三行的事。
